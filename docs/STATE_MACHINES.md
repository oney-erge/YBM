# Lifecycle boundaries

- `TaskRepository.apply_control` reads and applies pause, resume, and cancel under a SQLite write transaction. Repeated pause preserves the original resume state. `update_metadata` records in-flight worker results while retaining a concurrent pause; a terminal result observed during pause is restored when resumed.
- The operator worker checks the current task after model decision-making. Normal and approved single calls, and top-level parallel batches, are reserved under the same SQLite write boundary as pause and cancel: a control that wins first prevents dispatch. A call or batch reserved first may still run and finish after a later control. Its in-flight record remains until the result history or waiting transition is written, so a crash between effect and receipt remains visible. Cancellation remains terminal at the metadata-write boundary.
- Identical consequential calls within one parallel batch share one dispatch. A duplicate reflects the original result, including failure; distinct calls still run concurrently. After an interrupted batch containing a possible effect, the saved batch is presented for review rather than silently repeated.
- A delegate holds one conservative parent in-flight reservation across its substeps until its summary is committed. Each delegated single call or batch is checked against current controls and the reservation before dispatch. If a pause interrupts the delegate, resuming leads to review of possible earlier effects. A crash, timeout, or result-write failure with uncertain in-flight work also asks for review. These records do not prove that a dispatched external operation stopped or completed.
- Missing or malformed in-flight evidence is preserved for review, and a new reservation cannot overwrite it. Recovery treats low-risk outbound or mixed-capability calls, including message delivery, as potentially consequential; the risk label alone does not make a call read-only. This conservative rule can ask for review of an interrupted read in a mixed capability.
- Startup recovery leaves an unexpired worker claim alone. Before a different worker can reclaim an expired active task, the worker reconciles its saved in-flight record under a SQLite write transaction. A saved consequential single call is returned for user review rather than silently repeated. Before processing, a worker extends its still-owned, unexpired claim to cover the task's budget plus a buffer; it does not start if that claim was lost. Within the claimed worker context, task metadata updates and new call reservations recheck owner and expiry in the write transaction. A worker releases only its own claim. After a crash, recovery of a still-unexpired claim waits until the claim expires; expiry does not prove the old process or an external effect has stopped.
- Approval decisions and grant consumption remain in their existing policy/repository owners. An approval does not prove a remote effect happened exactly once. Claim checks prevent covered stale state writes and admissions, but cannot fence an already-dispatched operation or all other repositories and notification effects. External receipts and uncertain writes still need stronger reconciliation. A claimed row with a missing expiry is currently treated as eligible for recovery, not as evidence that its owner stopped. Pause status alone is not a distributed lock.
- The admin console and task-status tool expose state-based `allowed_actions` from the backend, with a fallback for older servers. A task-status result includes a bounded, redacted clarification question in the task row and, for up to three waiting tasks, in the summary consumed by the operator. This lets an agent understand what a task is waiting for without copying the underlying operation input. These actions are advisory snapshots: the command handler rechecks the current state, and separate policy or authorization can still reject a request. Existing status names and stored task rows are preserved; no schema migration is required for these control changes.

Focused checks are in `backend/tests/test_signals.py`, `test_storage.py`, and `test_worker_operator_loop.py`. Follow the repository setup prerequisite before running the backend suite. Do not infer live external-effect safety from these deterministic tests.
